## 0. 一句話

一個**本地優先**的修圖工具，讓不懂專業修圖軟體的人也能改圖：
用滑鼠圈出要改的地方，AI 只改那一塊，**本機負責合成**，
令圈選範圍以外的像素**逐 bit 保持不變**。

---

## 1. 目標與非目標

### 目標

- 給不會用 Photoshop 的人用。空間問題用滑鼠解決，不用文字描述
- **原解析度是預設值，不是進階選項**。4K 進去，4K 出來
- 一次一張，互動式。每次操作都有即時回饋
- BYO API key，不代使用者付費
- 非破壞性：每一次編輯是一層，不烤進原圖

### 非目標（明確不做）

- ❌ **批次處理**（使用者明確表示不需要——修圖逐張進行）
- ❌ 雲端存儲、帳號系統、託管服務
- ❌ 取代專業修圖軟體。這是給一般人的工具
- ❌ 訂閱制。工具本身不收費

---

## 2. 三個核心約束

### 約束 A：使用者不會用專業修圖工具

**後果：** 介面的每一個操作都必須是「看得出結果」的。

- 選取必須是**點擊**（指一下物件就選中），不是套索、不是圖層遮色片
- 不給專業術語。不叫「遮色片」，叫「要改的地方」
- 每一次生成之前要有**前後對照**，而且可以還原

### 約束 B：原解析度不可以無聲地流失

**後果：** 這是本專案成立的**唯一理由**。任何一個環節如果把解析度丟掉，
整個工具就失去意義。

→ 這決定了架構：**AI 只出一小塊，本機負責合成**。
→ 這也決定了要有**自動化測試**守住這件事（見 §5.4）。

### 約束 C：使用者自備 API key

**後果：** 成本是使用者自己的錢。要快取、要可切換模型、要跑前估價。
但**不是**所有操作都需要 API——見 §4 的分層。

## 3. 架構總覽

```
匯入圖片
  → 讀取真實格式（位元深度、色彩描述檔、EXIF）
  → 建立工作副本（浮點，原解析度）
        │
        ├─── 第一層：確定性調整（不經模型）
        │      曝光、白平衡、曲線、裁剪、拉直
        │      契約：無損，全解析度
        │
        ├─── 第二層：局部生成（patch）
        │      使用者圈選 → 裁切 → 送模型 → 收回
        │      → 量度校驗環 → 色彩／顆粒對齊 → 羽化合成
        │      契約：M_gen 以外逐 bit 不變
        │
        └─── 第三層：全幅生成（整張由 AI 產生）
               生成 → 放大
               契約：無（沒有可保留的東西）
        │
  → 匯出（原解析度、原格式、保留 EXIF）
```

**與 mangaMan 的關係：** 同一條原則的鏡像。
mangaMan 是「AI 只出文字，本機負責合成」；photoMan 是「AI 只出一小塊，本機負責合成」。
Provider 層（BYO key、逐任務路由、fallback、快取）直接沿用該專案的設計。

## 4. 三個品質層

**這三層的契約是相反的，不可以用單一 pipeline 硬套。**

| 層 | 內容 | 經過模型 | 契約 | 可自動驗證？ |
|---|---|---|---|---|
| **一、確定性調整** | 曝光、白平衡、曲線、裁剪、拉直、透視校正、縮放 | ❌ 完全不碰 | **無損**，原解析度進出 | ✅ 數學上精確 |
| **二、局部生成** | 移除物件、修補舊照、擴展畫布 | ✅ 只送遮罩區 | **`M_gen` 以外逐 bit 不變** | ✅ 精確比較 |
| **三、全幅生成** | 完全修改內容、風格重繪 | ✅ 送整張 | 無 | ❌ 只能靠人眼 |

### 4.1 為甚麼要分層

一般人所謂「修圖」，大部分落在第一層。裁剪、拉直、調光——
這些全部可以做到無損且即時，把它們交給生成模型是自找麻煩。

這與 mangaMan `render/erase.py` 的決策樹是同一條原則：
**便宜且確定的先做，貴且不可控的只在前者失手時才用。**

### 4.2 擴展畫布就是遮罩超出畫布的 inpaint

不需要為 outpainting 寫另一條路徑。原圖部分照樣逐 bit 保留，
新增區域就是「生成的 patch」，只是遮罩形狀超出了畫布邊界。

### 4.3 第三層會重新引入審查問題

第三層要把整張圖送出去。若日後要生成邊緣內容，這一層會直接撞上內容審查，
而第二層不會（因為只送一小塊，而且可以選擇完全不送）。
這個分岔要記在設計裡，不要在實作時才發現。

## 5. ★ 局部合成：校驗環機制

**這一節是本案最重要的部分。** 它回答的是：只把一部分交給 AI，
怎樣確保拿回來的圖能完美拼回原圖。

### 5.1 先把問題定義準確

**遮罩以外的像素根本不需要「拼」——只要不寫入那裡就可以了。**
合成時逐像素跳過，遮罩外就是原本的 4K 資料，一個 bit 都沒有動過。

所以真正的問題是**接縫**：生成的那一塊與周圍原圖交界處，為甚麼會被人眼看出來。

| 成因 | 具體表現 |
|---|---|
| 色彩與影調漂移 | 模型重繪一次，白平衡與對比不會與周圍一致 |
| 紋理統計不同 | 縮小再放大令顆粒感被磨平，放大時比周圍「滑」 |
| 內容不連續 | 模型看不到裁切圖以外的世界，牆線接到一半斷掉 |
| 尺寸與位移 | 回傳尺寸未必等於送出尺寸，重新取樣令特徵對不上 |
| 遮罩邊界本身 | 硬切留下硬邊；亂羽化出現鬼影 |

### 5.2 機制：留一圈校驗環

不要把遮罩的緊密外接框送出去，**要把外接框向外擴張一圈**。

```
┌─ C：送出去的裁切圖 ────────────────────────┐
│  ┌─ 校驗環（送給模型看，但我們不採用）──┐  │
│  │   ┌─ M_gen：要覆寫的區域 ────────┐  │  │
│  │   │                               │  │  │
│  │   │     ← 羽化帶在這一圈內 →      │  │  │
│  │   │                               │  │  │
│  │   └───────────────────────────────┘  │  │
│  └───────────────────────────────────────┘  │
└─────────────────────────────────────────────┘
```

這一圈同時做三件事：

1. **給模型上下文。** 模型看得到周圍的牆線、光線方向、材質，
   所以它生成的內容有機會接得上。這是解決「內容不連續」唯一有效的槓桿。
2. **我們丟棄它的渲染結果。** 校驗環只是給模型看的；
   合成時只採用 `M_gen` 以內的內容，校驗環的像素仍然來自原圖。
3. **★ 它是一枚校驗和。** 模型若守規矩，回傳的校驗環應該與送出的一模一樣。
   一旦有偏差，就知道它在不該動的地方動了手。

→ 於是在合成**之前**可以先量度「模型在被告知不要改的區域改了多少」，
偏離過大就**拒絕這張結果**，不合成。

> **核心原則：不是用提示詞拜託模型守規矩，是用幾何驗證它有沒有守。**

### 5.3 完整配方

#### 5.3.1 ★ 兩個遮罩，不是一個

**這是一個容易做錯、而且做錯之後症狀很難診斷的地方。**
正確做法是從使用者的選取**衍生出兩個獨立的遮罩**：

| | 給誰用 | 特性 |
|---|---|---|
| **去雜訊遮罩** `M_denoise` | 模型 | **接近二值**、稍微膨脹。**不可以是寬闊的柔和漸變** |
| **混合遮罩** `M_blend` | 合成器 | 有羽化。**柔軟度全部在這裡** |

**為甚麼不能把兩者合一——有論文證明：**

- **PELC（CVPR 2026）** 證明在潛空間用軟遮罩做線性混合**不等於**像素空間混合，
  因為 VAE 解碼器是非線性且空間糾纏的：
  `D((1-α)z_A + αz_B) ≠ (1-M)⊙D(z_A) + M⊙D(z_B)`。
  要還原真值編碼，一半以上的體素需要落在 `[0,1]` 之外的 α
  → 軟遮罩的潛空間插值會產生**無效的潛向量**，造成接縫、光暈、
  全域色偏，以及**遠離遮罩處**的劣化。
- **HarmonPaint** 量到注意力重加權的 τ 在 `[0.1, 0.6]` 最好，
  `τ ≥ 0.8` 直接失敗。
- **FLUX Fill** 對純 0/255 遮罩的結果最乾淨（灰色／反鋸齒會被當成部分條件）。

> **規則：模型拿到二值或輕微膨脹的遮罩；所有柔軟度在像素空間的合成 alpha 處理。**

**羽化半徑有下限：** 潛空間壓縮是 **8 倍**，所以
**小於 8 像素的羽化對模型等於不存在**。有用的羽化是 **16–32 像素**。

#### 5.3.2 完整配方

| # | 步驟 |
|---|---|
| 1 | 使用者圈選 `M`（緊貼物件，**要包含投影與倒影**——漏掉是最常見的使用者錯誤） |
| 2 | **遮罩前處理**（見 §5.3.3）→ `M_denoise`（二值、膨脹）與 `M_blend`（羽化） |
| 3 | `C = 膨脹(外接框(M_denoise), D)`——送出的裁切圖 |
| 3b | `D` **按比例取**：25–50% 的框大小，最少 64px。見 §5.3.4 |
| 4 | **檢查縮小倍率**——這決定畫質，見 §5.3.4 |
| 5 | 用 Lanczos 縮到模型原生尺寸；`M_denoise` 用最近鄰同樣縮放；維度補到 8 的倍數 |
| 6 | 送出。強度 0.75–0.85；**遮罩底下建議填模糊／邊界色，不是原始像素** |
| 7 | 收回後用同一個係數還原到 `C` 的精確像素尺寸 |
| 7b | **若縮小倍率 > 1.5×，補跑一次低強度（0.3–0.4）hires pass 在放大後的裁切圖上**——讓高頻被重新合成，不是被插值 |
| 8 | **量度校驗環偏差** → 超標則拒絕 |
| 9 | **色彩對齊**：用校驗環與原圖的統計，校正生成塊（整塊校正，不做局部混合） |
| 10 | **顆粒對齊**：估算原圖雜訊強度，加回等量顆粒 |
| 11 | 合成：用 `M_blend` 在**像素空間**貼回原圖位元組 |

**第 11 步是唯一寫入原圖的地方。** 它以外的地方，原圖位元組從未被碰過。

因此保證要精確地寫成：

> **`M_blend` 的羽化帶以外，像素逐 bit 不變。**

不是「使用者畫的線以外」，是自動膨脹與羽化之後的邊界以外。
**介面上應該把這條實際界線畫出來讓使用者看得到**，而不是用文字解釋。

#### 5.3.3 遮罩前處理

| 步驟 | 為甚麼 |
|---|---|
| **填內洞** | ⚠️ **SAM 產生的遮罩是有洞的、不連續的**（與 §7.2 的 SAM 弱點互相印證）。不填的話模型會在物件內部看到「保留」的指令 |
| **去斑點** | 過濾接近零的雜訊值 |
| **膨脹 8–16 px** | 約 1–2 個潛空間格，讓梯度資訊能跨越邊界流動 |
| **再模糊並二值化** | 得到 `M_denoise`。**膨脹要在羽化之前**，令模糊向外延伸進重生區，而不是向內侵入保留區 |

`M_blend` 則由原始遮罩以稍小的膨脹 + 絕對羽化（8–16 px）得出。

#### 5.3.4 上下文與細節會互相爭奪同一份預算

要給模型上下文，就要送比遮罩更大的範圍；但模型的輸出解析度是固定的。
**所以邊距 `D` 與遮罩拿到的細節，是從同一份預算裡分的。**

以遮罩 300×300 原生像素、模型上限 1024 為例：

| 邊距 `D` | 送出裁切 | 縮放係數 | 遮罩實際得到的模型像素 |
|---|---|---|---|
| 100 px | 500×500 | 2.05× | **615** ← 細節好，但**已進入「邊緣」區** |
| 362 px | 1024×1024 | 1.0× | **300** ← 上下文足 |

**★ 但真正決定畫質的不是邊距，是縮小倍率：**

| 縮小倍率 | 判斷 |
|---|---|
| ≤ 1.5× | 等於 1:1 或更好，沒問題 |
| ~2× | **邊緣**——區域本身細節少（天空、皮膚、散景）通常過關 |
| > 2–3× | 明顯比周圍低頻 |
| > 4× | 一眼看出 |

⚠️ **而且羽化救不了它。這是頻寬問題，不是接縫問題。**
唯一有效的對策是第 7b 步的 hires 補跑。

所以：

- **`D` 按比例取**（25–50% 的框大小，最少 64px），不寫死成固定像素數。
- ⚠️ **介面要顯示目前的縮小倍率**，因為那是畫質的實際決定因素，
  比「上下文的百分比」對使用者更直觀。
- ⚠️ **這個比例仍要做成可調的滑桿**——「接得順」與「有細節」
  在某些圖上確實需要人工取捨。
- ⚠️ **邊緣情況：** 遮罩貼著圖片邊界時，那一側沒有上下文可取，要另行處理。
- ⚠️ **大遮罩的退路：** 縮小倍率超過約 2×（遮罩大於畫面 25–30%）時，
  改用 2048 的模型，或把遮罩區切成重疊的 1024 視窗分別生成再融合。
  **遮罩超過畫面約 40% 時，實際上已是在做整幅重生，接縫風險急升**——
  這時應該改用第三層的路線。

### 5.4 怎樣驗證

**測試一（最大絕對通道差）**
合成之後，量度 `M_blend` 羽化帶**以外**的最大絕對通道差。

業界已有的門檻（`aitoolsguidebook.com` 提出的量度方法，2026-05）：

| 數值 | 判斷 |
|---|---|
| **0** | 逐位元貼回——真保證 |
| ≤ 2 | 無害的 VAE 往返量化 |
| **> 2** | **外滲（bleed）——失敗** |

**本專案的目標是 0，而且必須是 0**——因為我們在像素空間合成，
從來沒有寫入那一帶，所以 0 是達得到的。要用斷言守住，不是用「差不多」。

常見的外滲成因（按出現頻率）：整幅重生而只用遮罩當指引；
羽化／模糊的遮罩令混合帶內被部分重生；填補內距（32–64px）本身就碰到外面；
強度接近 1.0；VAE 編解碼；JPEG 匯出。

**測試二（接縫）**
計算 `∂M_gen` 上的梯度能量，與圖中其他位置的對照帶比較。
若兩者統計上無分別，就沒有可見接縫。
這是「看起來有沒有貼上去」的可自動化代理指標。

這兩個測試的意義與 mangaMan 用幾何審查當執漏閘門相同：
**把品質保證搬到機器驗得到的地方**，人眼只做最後一道。

### 5.5 幾個容易踩的細節

- **在線性光空間合成，不要在 sRGB 空間。** 在 gamma 編碼空間混合，
  邊界會出現暗邊或亮邊。這是常見的 bug。
- **中途絕對不要經過 JPEG。** 8×8 區塊痕跡不會與原圖對齊，
  而且會污染校驗環的量度。全部用 PNG 或 TIFF。
- **幾何全部用整數。** 裁切框、縮放係數、貼回位置——任何浮點漂移
  都會令特徵對不上，而這種錯位看不出原因。

### 5.6 為甚麼這個保證只能靠本地合成

**這一節是整個架構的正當性來源。** 實查到的證據（2026-09-18）：

**模型廠商自己承認會漂移：**

| 來源 | 內容 |
|---|---|
| **FLUX.1-Fill-dev 官方模型卡** | 承認填充區域以外有「輕微色偏」，填充區邊緣有「線條」 |
| **diffusers issue**（標題即為 `FluxInpaintPipeline overrides pixels outside the mask`） | 維護者回覆：VAE 編解碼不是無損，而 inpaint 權重是**刻意**訓練成跨接縫融合的 |
| **A1111 issue** | 遮罩外出現雜訊 |
| **Sygil-Dev 文件** | 遮罩外的區域**仍然會經過最後一次取樣**（這是刻意的設計） |
| **Photoshop Generative Fill** | 模型輸出 1024²，PS 把它**拉伸**去填滿較大的選取範圍，產生模糊塊、顆粒不符、平鋪痕跡。社群的變通做法叫「1024 規則」：固定 1024×1024 選取框，逐塊填，重疊約 200px，再手工羽化 |

**而聲稱做到的那些，沒有證據：**
Bria GenFill 聲稱「遮罩外像素完全保留，逐像素完美」——
但**沒有說明任何機制，也找不到任何第三方做過像素比對測試**。

> **結論：「遮罩外不變」只有在本地像素空間合成時才是真保證。**
> 當它是模型端的指示（遮罩條件、控制提示、inpaint 權重的學習式融合），
> 就**不是**保證，而且模型廠商自己都承認會漂移。
>
> **所以這個保證必須是合成器的架構性質，而不是關於模型的聲明。**

**這一點要寫進對外說明。** 使用者最初遇到的兩個痛點，
根源就在這裡——他當時用的工具把保證寄託在模型身上。

## 6. 資料模型

### 6.1 ★ 兩項已定稿的決定（2026-09-18）

**(a) 幾何是最後的輸出設定，不是圖層。**
裁剪、旋轉、拉直不佔圖層，只是匯出時的取景設定。

→ **推論：遮罩永遠存在原圖座標，不需要任何變換。**
這消除了整個「幾何變更令下游遮罩失效」的問題類別。
先裁剪再修圖在實務上不需要——因為內容一樣，取景只是最後的框選。

**(b) 運算用線性光 float32，但那是工作緩衝，不是儲存格式。**
理由見 §5.5——在 gamma 編碼空間混合會產生暗邊或亮邊，
而曝光的數學也只有在線性空間才正確。

**(c) ★ 底圖存原檔的位元組，按需要線性化。**（2026-09-18 定案）

實測發現真實照片最大 **42.2 MP**，不是本設計一直假設的 4K：

| 表示 | 42 MP 一張 |
|---|---|
| float32 線性光 | 506 MB |
| float16 | 253 MB |
| **uint8 sRGB（原檔的實際編碼）** | **127 MB** |

→ **底圖以原檔編碼儲存；只在處理某個裁切區時，才把那一小塊線性化。**

**這個決定有一個額外的好處，而且比省記憶體更重要：**
遮罩外的保證由「避免寫入」升級成**字面上的位元組複製**。
合成時把原圖位元組複製一份，只在遮罩內寫入——遮罩外的像素
根本沒有經過任何浮點運算，所以不可能有往返誤差。

**推論（會影響圖層的評估方式）：**

- 逐點運算（曝光、白平衡、曲線、對比）**與裁切可交換**——
  所以可以只對裁切區套用，不必materialize整張圖。
- 逐點運算也可以**合成成單一函數**，所以 N 個調整層等於 1 次運算，
  **沒有中間量化損失**。這正是 §12 講的「累積質素下降」的主要來源，
  在這裡被結構性地消除了。
- 空間運算（模糊、銳化、去雜訊）需要上下文，要帶邊距處理。
- **匯出時**才需要對整張圖評估所有圖層——分塊處理。

### 6.2 專案檔

```jsonc
{
  "schema_version": 1,

  "source": {                       // 原檔只引用，不複製
    "path": "…",
    "sha256": "…",

    "bit_depth": 16,                // 原始位元深度
    "icc_profile": "…",             // ★ 保留

  },

  "output": {                       // 幾何不佔圖層，見 6.1(a)
    "crop": [x, y, w, h],

      "crop": [x, y, w, h],         // 送出的裁切框（原圖座標）
      "scale": 0.2667,              // 縮小倍率（診斷用）
      "feather_px": 12,

      // ── 品質保證 ──

        "max_abs_diff": 0,          // ★ 目標必須是 0
        "at": "2026-09-18T…"
      },

      "cache_key": "…",             // hash(輸入 + 方法 + 參數 + prompt_v)
      "result": "cache/L_a91b04.png"
    }
  ]

```

### 6.3 重跑規則（mangaMan 的教訓）

**鐵律：重跑不可以悄悄覆蓋人工修改過的內容。**

| 情況 | 行為 |
|---|---|
| 參數未變 | 直接用 `cache_key` 取快取，**不重新呼叫模型、不重新付費** |
| 參數已變，`locked: false` | 重跑，更新 `result` |
| 參數已變，`locked: true` | **不覆蓋**，標記為「與目前參數不符」放進複核佇列 |
| 上游圖層改了 | 下游的 `cache_key` 失效，但 `locked` 的層仍然不覆蓋 |

**ID 是永久的。** 不可以「重新載入 = 重新派 ID」——
這樣做，第二天那個專案就廢了，因為所有人工調整都會對不上。

### 6.4 色彩空間的轉換點

```
原檔（可能 16-bit、有 ICC）
  → 解碼 → 線性光 float32          ← 內部工作空間由此開始
      → 圖層依序運算（全部在線性光）
          → 【模型邊界】轉回 sRGB 8-bit 送出
          → 【模型邊界】收回後轉回線性光
      → 合成
  → 匯出設定（裁剪、拉直）
  → 轉回 sRGB、指定位元深度、寫回 ICC 與 EXIF
```

⚠️ **模型邊界是唯一離開線性光的地方。** 任何其他地方的轉換都是 bug。

## 7. Pipeline 各階段

### 7.1 匯入與前處理

#### ★ 實測結果（2026-09-18，四張真實照片）

四張測試照片的實際情況，**三個發現全部會影響實作**：

| 檔案 | 格式 | 尺寸 | 像素 | ICC |
|---|---|---|---|---|
| diego-padilla | JPEG | 5304×7952 | **42.2 MP** | sRGB |
| denis | JPEG | 3581×5377 | 19.3 MP | sRGB |
| IMG_6166 | **HEIF** | 3024×4032 | 12.2 MP | **Display P3** |
| photo_2026-09-18 | JPEG | 1920×2560 | 4.9 MP | 無 |

**發現一：HEIC 必須支援。** 那是 iPhone 的預設格式，而 Pillow 本身
讀不到它（實測直接 `UnidentifiedImageError`）。需要 `pillow-heif`。
**沒有它的話，使用者從手機傳過來的第一張照片就會失敗。**

**發現二：真實照片比 4K 大得多。** 最大的一張是 **42.2 MP**，
不是本設計一直假設的 8.3 MP（4K）。後果是記憶體：

| 表示 | 42 MP 一張 |
|---|---|
| float32 線性光 | **506 MB** |
| float16 | 253 MB |
| uint8 sRGB（原檔的實際編碼） | **127 MB** |

⚠️ **這一項要在 P1 之前定案**（見 §14 第 18 項）。

**發現三：ICC 不可以假設是 sRGB。** iPhone 的照片是 **Display P3**。
把 P3 的數值直接當成 sRGB 用，飽和色會偏。
做法：載入時由來源描述檔轉到 sRGB（相對色度意圖——
保留色域內的顏色不動，只把色域外的裁剪掉；感知意圖會連色域內的
顏色都一起壓縮，對修圖工具不合適）。

⚠️ **已知限制：** 內部工作空間是 sRGB，所以寬色域原圖會被轉成 sRGB，
色域外的顏色會被裁剪。對一般輸出（網頁、社交）沒有影響，
但要記在帳上。

#### ★ 保證鏈的關鍵驗證：往返精確

**「遮罩外逐 bit 不變」要成立，``uint8 → 線性光 → uint8`` 必須精確。**
實測（2026-09-18）：

- 全部 **256 個灰階值**往返後逐值相同
- 一張 1474 萬像素的真實圖片，**最大差 0，不同像素 0 個**

這個失敗是靜默的——若不精確，整張圖每個像素都差一兩級，
看起來「差不多」，而保證已經破了。所以這寫成了正式測試
（`tests/test_image.py`）。

#### 匯入流程

| 步驟 | 做法 | 備註 |
|---|---|---|
| 讀取真實格式 | 位元深度、ICC、EXIF | ⚠️ 忽略 EXIF 旋轉是常見 bug |
| **先轉正，再轉色彩** | EXIF 方向 → ICC → sRGB | 轉色彩是有方向的運算，在躺平的圖上做要多一次轉置 |
| 轉內部工作空間 | 線性光 sRGB、float32 | 見 §6.1b |
| 匯出 | 轉回 sRGB、寫回 ICC 與 EXIF | **方向標籤要移除**——像素已轉正，留著會令看圖軟體再轉一次 |

⚠️ **Pillow 的陷阱：16 位元的 RGB PNG 會被悄悄轉成 8 位元。**
所以 `bit_depth` 對那類檔案會回報 8，而真實來源是 16。
要準確知道需要自己解析檔案標頭（見 §14 第 19 項）。

### 7.2 選取（點擊分割）

「很難仔細地叫 AI 修那一部分」的技術答案不是更好的提示詞，是**點擊分割**。

Meta 的 SAM 系列可以用一個點擊取出任意物件的遮罩，不需要套索技巧。

#### ★ 一個驅動整個選型的架構事實

**SAM 系列內部一律把輸入縮到 1024×1024。** 所以 4K 原圖只增加
「縮放 + 遮罩放大」的成本，不增加編碼器成本。

→ 即是：**選取的時間與原圖大小幾乎無關。** 這對本案很有利。

#### 實查結果（2026-09-18，CPU 為 i7-9700 推算值）

| 模型 | 授權 | 大小 | CPU 速度 | ONNX | 備註 |
|---|---|---|---|---|---|
| **MobileSAM** | **Apache-2.0** ✅ | 40.7 MB | **0.7–0.9 秒** | ✅ 官方 | ★ **首選** |
| SAM 1 ViT-B | **Apache-2.0** ✅ | 375 MB | ~4–5 秒 | ✅ 官方 | onnxruntime + numpy 已足夠，不需 torch |
| SAM 2.1 | **Apache-2.0** ✅ | 78–450 MB | 未實測 | ✅ 官方 | 小物件比 SAM 1 好 |
| FastSAM-s | ⚠️ **AGPL-3.0** | 23.9 MB | **~58 毫秒** | ✅ | 最快，但它不是真正的可提示分割器（底層是 YOLOv8-seg） |
| SAM-HQ | **Apache-2.0** ✅ | 與 SAM 同級 | CPU 上不互動 | ❌ 只有社群 | 頭髮／細結構最好，**留待有 GPU 時用** |
| **EdgeSAM** | ⚠️⚠️ **NTU S-Lab 非商用** | ~40 MB | 最快 | ✅ CPU 優先 | ★★ **CPU 上最好的模型，但不能用** |
| SAM 3 | 自訂「SAM License」，非 OSI | ~3.5 GB | **CPU 不可行** | ❌ | 權重需申請；**注意 SAM 2 是 Apache 而 SAM 3 不是** |

**選型：MobileSAM 為主力**（Apache-2.0、官方 ONNX、CPU 上 0.7–0.9 秒，
互動感足夠）。**FastSAM-s 作為可選的即時預覽**（AGPL 在純自用下不觸發，
但要記在 §13）。**有 GPU 之後加 SAM-HQ 處理頭髮。**

⚠️ **已知弱點（所有 SAM 系列共通）：** 頭髮與樹狀結構會被當成紋理而過度分割；
玻璃／鏡面會分割到**後面**的內容；低對比與嵌入物件較弱。
這些是模型特性，不是提示詞或微調可以解決的。

⚠️ **而且 SAM 的輸出遮罩是有洞的、不連續的**——所以 §5.3.3 的
「填內洞」不是可選項。不填的話，模型會在物件內部看到「保留」的指令，
結果是物件沒有被完全移除。

### 7.3 第一層：確定性調整

⚠️ 待定。技術上最簡單，但不是第一個要做的（見 §11）。

### 7.4 第二層：局部生成

見 §5。實作時要決定：

- **哪一個模型真正接受遮罩輸入**（vs 只是用文字拜託它不要改）——⚠️ 待實查
- 本地 inpainting（LaMa 這一類）是否應該當作**預設路徑**——見 §7.4.1

#### 7.4.1 最常見的操作可能完全不需要 API

「移除多餘物件」若可以用本地的 inpainting 完成——它**天生就是遮罩原生**的，
遮罩外保證不變，CPU 上跑得動，而且免費——那麼：

> **你要的那個硬保證，在沒有 API 的情況下就已經做得到了。**

API 應該保留給本地 inpainting 做得不好的情況：
大面積、複雜材質、需要**語意替換**（不只是移除，而是要變成別的東西）。

→ 這決定了 §11 的實作順序，也決定了離線狀態下核心保證仍然成立。

#### ★★ 實測結果（2026-09-18，真實照片）

在真實照片上移除三顆骰子（遮罩 0.30 MP，裁切 1228×1134）：

| 引擎 | 時間 | 校驗環 | 填補品質 |
|---|---|---|---|
| **LaMa** | **13.5 秒** | **24.0** | **幾乎看不出接縫**——布的顆粒質感連續 |
| Telea | 1.2 秒 | 0.0 | **一眼看出**——大片平滑的多邊形灰塊，沒有顆粒 |

**結論：LaMa 是本地路徑的主力引擎，不是 Telea。**
LaMa 的填補說服力遠勝傳統方法，代價是慢十倍（13.5 秒 vs 1.2 秒）。
對逐張修圖而言 13.5 秒可以接受。

#### ★★ 這個實測否證了「校驗環可以當品質閘門」

**LaMa 是遮罩原生的模型，卻把「被告知不要改」的區域改了 24–27 級**
——因為它整張重繪，加上 512 往返的重新取樣。

**這正是 §5.6 的實證：保證只能來自合成器，不能來自模型。**
但它同時推翻了原本的設計：

> **校驗環的大小與填補品質無關。**
> LaMa 是 24–27 而品質好；Telea 是 0 而品質差。

所以校驗環是**診斷數字，不是品質閘門**。憑它自動否決會錯殺。
門檻只有在「模型聲稱會保留遮罩外」時才有意義（例如 API 模型）。

#### 兩個實作上的發現

**一、遮罩必須完整蓋住物件。** 第一次測試時我的橢圓在骰子底部留了一條邊，
LaMa 把那些殘留的暗色**延伸進洞裡**，產生大片暗影。
遮罩沒蓋好的代價比想像中大——它不只留下殘影，還會污染填補。

**二、⚠️ 這個 ONNX 的空間維度固定是 512×512。** 裁切圖大於 512 就要
縮小進去、放大回來。對 LaMa 而言代價比帳面上小（填補區本來就平滑），
但**真正大的裁切圖應該切塊處理再融合**——列為 §14 待實測項。

### 7.4.2 修補舊照片：多數可以離線完成

這一類與其他四類不同，它主要靠**修復模型**，不是生成模型。
實查結果（2026-09-18）：

| 需求 | 建議做法 | 是否生成式 | 授權 |
|---|---|---|---|
| 薄刮痕、裂痕 | 傳統 CV（Telea / PatchMatch），大面積才用生成 | 否 | — |
| 刮痕**偵測** | Microsoft 舊照修復的專用偵測器，**直接給你遮罩** | 否 | **MIT** ✅ |
| 掃描件雜訊 | SCUNet | 否 | Apache-2.0 ✅ |
| 褪色 | **逐頻道直方圖拉伸 + 中性灰平衡** | 否 | — |
| 模糊、失焦 | Real-ESRGAN `x4v3`（小，5 MB）／ SwinIR | 否 | BSD-3 ✅ |
| 人臉模糊 | **RestoreFormer** | 否 | Apache-2.0 ✅ |

**兩個關鍵判斷：**

**(a) 色彩還原用傳統方法不只是「夠用」，它在數學上更正確。**
褪色是**每個色頻的密度衰減**，所以「逐頻道直方圖拉伸 + 中性灰平衡」
就是它的正確逆運算，而且是確定性的、可重現的、不會編造顏色。
擴散模型做色彩化會**產生看起來合理但不存在的顏色**——對修復而言這是致命的，
因為它給你一張好看但假的照片。**先用傳統，只在明顯不足時才升級到模型。**

**(b) 去雜訊要分雜訊類型。** 對合成的加性高斯雜訊，BM3D 這一類傳統方法
有競爭力（有比較顯示 BM3D 在一組測試上勝過 U-Net CNN 3.24 dB）；
但**掃描件的雜訊是掃描器／JPEG／底片顆粒，不是加性高斯**——
這一類清楚是 SCUNet 這一類學習式方法較好。

→ **結論：修補舊照片有很大一部分可以是純本地、零成本、而且比生成式更忠實。**
生成式重建人臉會「編」出不存在的細節，對舊照片往往不是使用者想要的。

### 7.5 第三層：全幅生成

⚠️ 待實查。與第二層的解析度策略**剛好相反**：

- 第二層：有真正的 4K 像素，所以放大是**缺陷**
- 第三層：沒有任何原有像素，放大是**流程的正常一環**

路線：先用原生支援高解析度的模型，不夠再用本機放大模型收尾。

## 9. 硬體分層

**與 mangaMan 不同，本案對硬體的要求寬鬆得多。**

因為**不做批次、逐張修圖**：

- 單張等 30 秒可以接受；180 頁等 45 分鐘不可以
- → 不需要任務佇列、不需要斷點續跑、不需要隔夜模式
- → **Tier L（無 GPU）的痛大幅減輕**

| Tier | 條件 | 能力 |
|---|---|---|
| **S** | NVIDIA ≥8GB | 分割、inpainting、修復、放大全部 GPU |
| **M** | NVIDIA 4–6GB / AMD DirectML | 同上，較慢或需細 batch |
| **L** | 純 CPU | 輕量分割 + 本地 inpainting + 修復模型慢跑；生成式走 API |

**反過來，延遲變得非常關鍵。** 互動式使用下，
非同步回報進度與可取消，比批次吞吐量重要得多。

## 10. 成本模型

使用者自己付錢。手段與 mangaMan 相同（快取、逐任務派 model、跑前估價），
另加本案特有的一項：

**先試本地，失敗才走 API。** 這是最大的成本槓桿，而且是免費的——
因為本地路徑（見 §7.4.1）同時也是品質更好的一條路。

## 11. 路線圖

**北極星指標：每張圖的人工秒數。**

### 為甚麼由第二層先做，不是第一層

- 第一層技術上最簡單，但它**不解決最初的痛點**。先做它，
  等於先做了一個使用者本來就做得到的工具。
- **第二層才是原本就想要的那件事**——「仔細地修某一部分，而且不掉質素」。
  它同時驗證三個最關鍵的假設：點擊選取好不好用、
  合成能不能做到遮罩外逐 bit 不變、以及各家模型的 patch 品質如何。
- 第一層可以在第二層的框架上後補，介面共用。

| 階段 | 內容 | 完成標準 |
|---|---|---|
| **P0 骨架** | 資料模型、匯入（保真）、Konva 畫布、Provider 層 | 能把一張圖載入、圈選、匯出，像素逐 bit 不變 |
| **P1 局部生成** | 點擊分割、校驗環、色彩／顆粒對齊、羽化合成、兩個自動化測試 | ★ **移除一個物件，接縫看不出來，測試通過** |
| **P2 確定性調整** | 曝光、白平衡、曲線、裁剪、拉直 | 無損且即時 |
| **P3 修補舊照** | 去雜訊、色彩還原、放大、人臉修復（多為本地模型） | 一張舊照端到端修好 |
| **P4 全幅生成** | 整張生成 + 放大策略 | 可以完全由 AI 產生一張圖 |
| **P5 收尾** | 非破壞性圖層、重跑規則、匯出保真、EXIF | 來回編輯多次而無累積損失 |

## 12. 風險與已知限制

| 風險 | 緩解 |
|---|---|
| **累積質素下降** | 若每次編輯都經過模型且互相疊加，質素會逐次複合下降——這正是最初的痛點，只是會累積。**必須用非破壞性圖層 + patch**，只有被編輯過的區域會變 |
| 校驗環偏差被忽略 | 量度值要顯示給使用者，不能只是內部數字 |
| 生成區域「看起來像貼上去」 | §5.3 第 7、8 步；並提供 100% 縮放的前後對照 |
| 模型回傳尺寸不符 | 不接受模型自選尺寸；記錄整數縮放係數，必要時用校驗環做對齊檢查 |
| 選取不準（頭髮、透明物體） | ⚠️ 待實查：分割模型在這些情況的已知弱點 |
| 全幅生成撞審查 | 第三層限縮使用；第二層可完全不出本機 |
| 本地模型在 CPU 上太慢 | 逐張使用令等待可接受；進度回報與可取消 |

**現時純自用，所以從寬處理**（與 mangaMan 同一路線，該專案處理此事的經過見其

| 字體 | 思源黑體 / Noto Sans CJK | OFL | |

### 13.2 ★★ 兩個必須記住的陷阱

**兩者都是 NTU S-Lab 非商用授權，兩者都是「同類中最好但不能用」：**

| 模型 | 它是甚麼 | 為甚麼危險 |
|---|---|---|
| **EdgeSAM** | CPU 上最快的分割模型 | 效能遠勝 MobileSAM，很容易順手選它 |
| **CodeFormer** | 效果最好的人臉修復 | 同樣是順手就會選的那一個 |

還有一個容易誤判的：**SAM 2 是 Apache-2.0，但 SAM 3 不是**（自訂
「SAM License」，非 OSI，權重需申請）。**不要假設同一個家族共用授權。**

另有兩個「看起來寬鬆但內含污染」的：**GFPGAN**（Apache-2.0，
但內含 DNet 是 CC BY-NC-SA 4.0）與 **FastSAM**（權重標 Apache，
但 Ultralytics 實作是 AGPL-3.0）。

⚠️ 上述每一項在**散布前**都要重新核實一次，不可只依賴本表。
授權條款會變，而 HF 上轉換版本的授權標示歷來不可靠
（mangaMan 就遇過把 GPL-3.0 權重標成 Apache-2.0 的例子）。

**純自用的邊界與 mangaMan 相同：** 純自用不受影響，只在散布時觸發。
**但在任何散布（公開發布、分享他人、放上平台）之前必須回頭處理這一節。**

### 14.1 RETHINED：已查，**否定**（2026-09-18）

原以為這條非擴散路線可能是 Tier L 的救星。**結果不是，而且原因不是速度。**

**致命的三點：**

1. **沒有權重，而且永遠不會有。** 作者在 2026-01-30 的 issue 明言
   「由於我博士研究的性質，沒有計劃釋出訓練程式碼或權重」，
   2026-06 再次確認。**這單獨一項就終結了它。**
2. **連已釋出的程式碼都跑不動。** `model.py` 匯入 `mobileone`，
   而 `mobileone.py` **不在 repo 內**（issue #20，2026-09-10 仍然開啟）。
   作者承諾會補上但一直沒有。
3. **沒有 LICENSE 檔案。** 即使程式碼能跑，也沒有任何使用授權。

**而速度宣稱本身也站不住：**

- 論文**從未說明**量度是在 CPU、GPU 還是 NPU 上做的，只寫裝置名稱。
  從 CoreML fp16 與 ONNX 的用法推斷，那些是**加速器數字，不是 CPU**。
- **論文自己的表 2 就打臉摘要**：摘要寫「多種行動裝置 30 毫秒以內」，
  但五部裝置中只有一部低於 30 毫秒。

**最關鍵的是它訓練在不同的問題上：**

DF8K-Inpainting 是 2,850 張**戶外風景**圖，**明確不含人物**，
遮罩是 30–50% 的自由形狀。而人物移除的遮罩通常是 5–20%。

→ **對「移除路人」這個用途，它是雙重的分布外**（訓練集沒有人；
而且遮罩大小也對不上）。作者自己承認失效模式是
「以平均現有特徵來填充，產生模糊效果」。

**結論：當作論文與資料集的貢獻看待，不是可用的模型。**

### 14.2 ★ 但查出了更好的東西：LaMa via OpenCV

同一份調查找到真正可行的那條路：

| 項目 | 內容 |
|---|---|
| 來源 | `opencv/inpainting_lama`（HuggingFace） |
| 授權 | **Apache-2.0** ✅ |
| 形式 | OpenCV 官方 ONNX 封裝，fp32 加一個量化版本 |
| 需求 | OpenCV ≥ 5.0.0 |
| 上游 | Carve 的 `lama_fp32.onnx` |

**這解決了 §14 第 6 項（LaMa 授權待核）——答案是 Apache-2.0，可用。**

⚠️ **已知代價：** OpenCV 的審查者指出在 CPU 上模型載入與處理時間**相當可觀**；
LaMa 原生約 2K，4K 要切塊處理。

⚠️ **與本案的關係：** LaMa 的輸出本身**不是**邊界精確的
（它是純前饋，`out = pred*mask + orig*(1-mask)` 會令遮罩邊緣有少許差異）。
但這不影響本案的保證——**我們的合成器從來不寫入遮罩外**，
而遮罩內的少許邊緣差異由 §5.3.2 第 11 步的羽化合成本來就會處理。
真的需要時可以在合成前對生成塊做一次 `seamlessClone`（Poisson），
但要注意 Poisson 會同時改動生成塊的內部，反而失去對生成內容的精確控制——
**預設不用，只在有明顯低頻光照不匹配時才考慮。**
