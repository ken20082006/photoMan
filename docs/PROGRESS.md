# photoMan — 進度與交接

> **這份文件是為了換 session、換電腦、或隔一段時間回來時用的。**
> 讀完這一頁就應該能繼續開發，不需要翻對話紀錄。
> 每次工作結束前，更新「[現況](#2-現況)」與「[下一步](#6-下一步)」兩節。
>
> 最後更新：2026-09-20（雲端編輯的顏色、拖曳與放大、匯出格式）

---

## 1. 一句話

`C:\photoMan` 是一個本地優先的修圖工具，讓不懂專業修圖軟體的人也能改圖：
用滑鼠圈出要改的地方，AI 只改那一塊，**本機負責合成**，
令圈選範圍以外的像素**逐 bit 不變**。

完整設計見 [`design.md`](design.md)。

### ★ 介面已經可以用（2026-09-18）

```powershell
.\.venv\Scripts\photoman.exe ui
```

會自動開瀏覽器。流程：拖入照片 → 在物件上按一下 → 按「移除選中的東西」
→ 前後對照 → 匯出。

**實測（真實照片，19.3 MP）**：開啟 2.2 秒、點擊選取 0.5 秒、
移除 14.9 秒、匯出 **3581×5377 的原解析度** 16.3 MB。

⚠️ **一個重要的校準：** 先前那些看起來很明顯的「鬼影」對照圖，
每一張都是 50% 裁切——等於在 **200% 縮放下檢視**。
縮到全圖的正常觀看尺寸，移除效果是好的；只有放大細看才見痕跡。
判斷這類結果時要記住這件事。

### ★ 手動圈選：我畫的就是遮罩（2026-09-19）

**這是一個方向修正。** 原本的設計寫著「選取必須是**點擊**，不是套索」
（見 §4）。但實際用起來，點擊分割回答的是「**這一團像素是甚麼**」——
那在物件邊界清楚時很好用，可是：

- 使用者心裡已經有一條明確的界線時，SAM 的判斷只是多一個出錯的地方
- 要改的東西根本**不是一個物件**：一片天空、一條裂痕、一段文字、
  一個大區域裡的一小角。點下去 SAM 只會選中它認得的那件東西

→ 所以現在有三個工具，**預設是手動的**：

| 工具 | 做法 |
|---|---|
| 筆刷 | 拖曳塗抹。筆畫在瀏覽器上畫，**放手才送一次** |
| 方框 | 拉一個矩形，矩形本身就是遮罩 |
| 自動 | 點一下，交給 MobileSAM（原本那條路，保留） |

**技術上最重要的一點：那一筆是在瀏覽器上畫的，不是在伺服器上。**
塗抹要跟得上滑鼠，所以筆畫在畫布上以一條 Konva 圖形呈現（零延遲），
放手才把**一張預覽解析度的點陣圖**送給伺服器換算成原圖座標。

座標換算仍然只有一個地方要做（`server.py` 的 `_decode_mask_png`），
但這次多了兩個要小心的細節：**放大用雙線性而不是最近鄰**
（最近鄰會令筆畫邊緣留下比羽化半徑還粗的階梯），
以及**疊圖只在預覽解析度上色**（42 MP 的圖若先造全解析度 RGBA
再縮小，每一筆要配置近 200 MB）。

**實測（`sandbox/manual_e2e.py`，12 MP 的圖）**：開啟 1.1 秒、
框選 0.06 秒、移除（LaMa）9.5 秒、**框外被動過的像素 0 個**。

**另一層驗證：`sandbox/browser_check.py`。** 用 headless Chrome 載入
真的頁面，合成滑鼠事件真的畫一筆、拉一個框。合成遮罩那條路有 pytest
守著，但「拖曳真的會產生一筆」只有在瀏覽器裡才驗得到——事實證明
這一層有價值：第一次跑就抓到事件送錯元素（Konva 把 DOM 監聽器綁在
`stage.content` 上，不是 `stage.container`）。

### ★ 匯出改為 WebP（2026-09-20）

使用者反映「輸出成品比原圖都大」。實測那張 18.4 MP 的照片
（原檔 JPEG 5.05 MB）：

| 格式 | 大小 | 時間 | 差異 |
|---|---|---|---|
| PNG（先前） | 17.32 MB | 1.2s | 逐位元相同 |
| WebP 無損 | 11.85 MB | 11.4s | 逐位元相同 |
| **WebP q95（現在預設）** | **3.49 MB** | 3.0s | 平均 0.95 級 |
| JPEG q95 | 5.43 MB | 0.1s | 平均 0.60 級 |

PNG 比原檔大 3.4 倍——存照片用 PNG 本來就是浪費。

**WebP 無損不值得**：只小 32%，卻慢十倍。
所以做成兩個選項：WebP（檔案小，預設）與 PNG（完全不失真）。

⚠️ **測試要注意**：預設變成有損之後，凡是「逐位元比較兩次匯出」的測試
都要明確指定 `?format=png`——有損編碼會令本來相同的區域因為旁邊的內容
不同而編出不同的位元組。那是編碼器的性質，不是 bug。

### ★★ 雲端模型：色差、參考圖、拖曳與放大（2026-09-19／20）

使用者用雲端模型移除人物之後反映「成品有明顯色差」。查下來是**三件
互相獨立的事**疊在一起，而且**最嚴重的那一件是我們自己的 bug**。

#### ① `match_colour` 會抹掉使用者要的改動

它把生成塊的平均色**強行拉向周圍**。對 LaMa 的填補這是對的（填出來的
東西本來就該像周圍），對語意替換是**反效果**：

| | |
|---|---|
| 指令 | 「把衣服改成紅色」 |
| 周圍 | 綠草 (90, 130, 60) |
| 模型畫的 | 紅 (170, 40, 40) |
| 經過 `match_colour` 之後 | **(89, 129, 60)** ← 變成周圍的綠色 |

所以 `match_colour` 加了 `intent`：`fill`（對到周圍）與 `edit`
（只扣掉模型的整體漂移，用遮罩外的環量度）。

#### ② 但「由引擎猜意圖」是錯的——這是這次最貴的一課

第一版用引擎判斷（雲端＝edit、本機＝fill），看起來很合理。
**用真實圖層量出來卻是反的**：

| 使用者真實的指令 | 填補意圖的落差 | 編輯意圖的落差 |
|---|---|---|
| `移除人物` | **2.4 級** | 22.8 級 |
| `移除人物` | **3.9 級** | 38.6 級 |
| `將人物向右移到路中間` | 11.4 級 | 11.6 級 |

同一個模型兩件事都做得到，而兩者要的對齊是**相反的**。
引擎回答的是「它怎麼畫」，不是「使用者要甚麼」。

→ 第一版加了兩顆按鈕讓使用者選。**後來拿走了**（使用者回報：
「係咪冇用，可以拎走」）——那個選擇本身才是負擔，而且使用者第一次
用就會遇到「我怎麼知道該選哪個」。

→ 現在是一條固定的產品規則：**本機＝填補，雲端＝編輯**。
介面直接寫明「只是要移除東西的話用本機」。規則只有一條，而且
失敗是**看得見的**（用雲端移除會與周圍有色差，而那正是警告會講的事）。

#### ③-b 修正：「在哪裡量」比「扣多少」重要（2026-09-20 晚）

使用者回報「用換成・加入還是有點色差」。案例是**改髮型**（用參考圖），
遮罩是框住整個頭的大方框。量出來：

| | |
|---|---|
| 背景（遮罩外的環）的偏移 | −10.8 |
| 臉的偏移 | **−5** |
| 扣掉環的偏移之後，臉的殘餘差 | **+8.9** |

**「模型的色偏在全圖一致」這個假設不成立。** 把背景的偏量套到臉上會過頭。

→ 改成在**模型自己保留的內容**上量偏移：遮罩內挑出
`|模型 − 原圖| < 8` 的像素，那裡我們知道真值。遮罩內幾乎沒有保留區時
（模型把整塊換掉，例如純粹的移除）退回用環量。

實測（使用者三個真實圖層、三個不同模型）——「模型保留區」的殘餘差：

| 案例 | 不修正 | 用環量（舊） | 用保留區量（新） |
|---|---|---|---|
| 移除人物 ①（gemini-3.1-flash-lite-image） | −3.0 | −3.5 | **−0.3** |
| 移除人物 ②（grok-imagine-image-2.0） | −1.8 | −1.3 | **−0.3** |
| 改髮型（gpt-5.4-image-2） | −3.5 | +8.9 | **−0.3** |

門檻為甚麼是 8：實測模型的描繪誤差是 1–5 級，而使用者要的改動大得多
（改髮型是 50 級）。門檻放到 20 會把「使用者要的細微改動」（例如
「調暗 15 級」）也當成誤差而抹掉——實測偏移量會由 +0.4 漲到 +2.9。

#### ③-c 但真正看得見的色差是「框太大」

同一張圖，把使用者的方框切成九宮格，看成品與原圖的差：

```
+19.8   +65.8   +42.6   ← 上排：湖水、石頭（本來不該動）
 +9.3    -4.2    +4.7   ← 中排：臉（新做法修好了）
 -6.8    -9.8    +0.3   ← 下排：衣服
```

**框內上排的背景被模型改了 +20 到 +66 級**——那才是使用者看到的那個
方框邊界。他的方框框住了整個頭**加上一大片背景**。

這件事程式修不了（模型只收到一張圖加一句話，它不知道框內哪部分不該動）。
介面現在會在框太大時提醒：

> 會交給雲端模型——框很大，它會把整個框重畫

#### ③ 第一版：用遮罩外的環量漂移（**已被 ③-b 取代**）

| 模型 | 整體漂移（環 vs 環） | 當時的 fill 意圖扣的 |
|---|---|---|
| gpt-5.4-image-2 | +12.7 | +4.5 |
| seedream-4.5 | +25.6 | +3.9 |

（LAB 的 L 通道。）當時的結論是「漂移扣得不夠」，所以改成用環量。
**那個結論只對了一半**——見 ③-b：更大的問題是「在哪裡量」。

#### ④ 校驗環量度 255（滿級）——我們算了卻從來沒說

那代表模型把「被告知不要改」的區域改了 255 級，**整張重畫**。
`EditResult.is_trustworthy(API_THRESHOLD)` 就是為此而寫的，
而它**從來沒有被呼叫過**；介面無條件寫著「選取範圍以外完全沒有改動」。

→ 現在會在成品下方顯示：

> 這個模型沒有照遮罩辦事：它在你圈選的範圍之外也改了 255 級（滿級），
> 也就是把整張重新畫了一遍。……框得越緊，這個問題越小。

**不否決結果**——那是使用者已經付錢的呼叫，而且合成器本來就守住了遮罩外。

#### ⑤ 參考圖：把圖片餵給模型

`providers.edit(references=)`、`ApiInpainter(references=)`、
介面的「加入參考圖」。縮圖留在瀏覽器，按執行時才送出，送出前先在
瀏覽器縮到 1536（原檔可能十幾 MB）。張數上限由模型決定
（`ImageModel.max_references`，網路上已經有這個資訊，只是沒用），
扣掉「標了紅色的選取範圍」那一張。

#### ⑥ 拖曳與放大：兩個都是實測到的缺口

**拖曳完全沒有實作**，而提示卻寫著「拖曳移動」。更糟的是在照片外面
拖曳會**沿著邊緣畫一筆**（實測 34,145 個像素）——`beginStroke` 用了
`clampToImage`，把界外的點夾到邊緣照樣畫。

現在：**按住右鍵拖曳**（中鍵也可以）、起筆用 `pointerToImage()`
（界外整個放棄）。**平移不佔一個工具按鈕**——它是隨時要用的動作，
不應該逼使用者在「畫」與「移動」之間切來切去。

**自己實作平移而不用 Konva 的 drag**——不必猜 Konva 的內部狀態，
而且我們本來就需要一個「視野變了」的鉤子去重抓放大時的細節。

**縮放列放在畫布左上方**（與市面上的修圖工具一樣）：`− 100% ＋ 適合視窗`。
按百分比回到 100%——**那個百分比是相對原圖的**，不是相對預覽。
有了 `/api/detail` 之後 100% 是真的做得到。

**放大看到的從來不是真像素**：預覽最長邊 1600，3213×5712 的圖在畫布上
只有 0.28 倍。放大 4× 時高頻細節只剩一半（9.7 → 5.5），
23% 的像素差超過 10 級。

→ 新的 `/api/detail`：**由原檔裁出那一塊、縮到螢幕要的尺寸**。
關鍵是「由原檔重新取樣」而不是「送原解析度」——送原解析度的話，
放大 1.2 倍就要傳 8 MP，而螢幕根本顯示不了那麼多。

### ★★ 多步編輯：一張照片只能改一次（2026-09-19）

**這是使用者實測之後發現的，不是從程式碼看出來的。**

使用者連續改了兩處，發現第二處把第一處的成果毀了。量測（`sandbox/two_edits.py`）：
先移除 A，再框 B 執行，**A 區域 12000 個像素裡有 11997 個被重新生成**。
三個原因互相加乘：

1. 執行完**遮罩沒有清掉**，第二次是 A ∪ B 一起送
2. 裁切區因此變大 → LaMa 的 512 縮放倍率改變 → 整塊內容都不一樣
3. 每一次執行都套用在 `SESSION.base`（最原始那張）上，**成品不會回流**

**修好之後：0 / 14400。**

#### 做法：圖層只存貼片，成品是「算回來」的

一層需要的只有**裁切框、遮罩、貼片**三個東西，因為
`composite_patch_into_bytes` 是純函數。所以：

- 記憶體裡一層只佔**裁切區那一小塊**（約 0.5 MB），不是整張遮罩（42 MP 是 42 MB）
  ——`plan_crop` 保證遮罩完整落在裁切框內，所以框外一定是空的
- 復原 = 丟掉最後一層，然後 `render(source, layers)` **整個重播**（複製 + 幾次貼上，毫秒級）
- 存檔時貼片寫進 `cache/<layer_id>.png`——P0 的 `ProjectStore` 本來就是這樣設計的，
  只是從來沒有被呼叫過

**貼片要存「色彩與顆粒對齊之後」的那一個**，不是模型的原生輸出——
對齊需要 `base_crop` 與遮罩，那兩個在重播時未必能重建。

**「working 永遠等於 render(source, layers)」是一個不變式**，有測試守著。
執行之後直接沿用結果（省一次全圖重播），兩條路因此有分岔的機會。

#### 界線變了：由「遮罩外」升級成「所有寫入範圍的聯集之外」

每一步都在 alpha 為 0 的地方做位元組複製，所以歸納下來就是
**「所有圖層的寫入範圍聯集之外，位元組等於原檔」**。

⚠️ 寫入範圍**不是使用者畫的那條線**——羽化會向外擴一圈。算界線要用
`blend_alpha_for`，**不可以自己手寫膨脹**：OpenCV 的橢圓結構元素下
`dilate(dilate(m, a), b) ≠ dilate(m, a+b)`。

#### 42 MP 上的實測（2026-09-19）

| 操作 | 時間 |
|---|---|
| 開啟（含 SAM 嵌入） | 2.4 秒 |
| 一層編輯（Telea，裁切 400×200） | 2.2 秒 |
| **復原**（重播 2 層） | 2.5 秒 |
| **重做**（重播 3 層） | 3.3 秒 |
| 匯出原解析度 PNG（105 MB） | 4.0 秒 |

編輯的 2.2 秒幾乎全部是 `prepare_masks` 在 42 MP 上算 alpha，不是引擎。
**圖層的記憶體與磁碟成本都可以忽略**（一層的裁切區遮罩加貼片是零點幾 MB）；
真正的成本是「每一層都要重算一次全圖的 alpha」，而那只在編輯與復原時付。

#### 順手修好的兩件事

- **SAM 的分割跑在 `working` 上，而且帶了 `revision`。** 先前跑在 `base` 上，
  編輯過之後「自動選取」會選到一個畫面上已經不存在的東西；嵌入快取的鍵
  只看粗取樣，移除一個小物件根本不會改變那些取樣點。
- **`Checksum.max_abs_diff` 可以是 `None`。** 校驗環量度可能是 `nan`
  （遮罩填滿了整個裁切區），而 JSON 沒有這個值——寫進專案檔會令它讀不回來。

### 已經完成並通過測試的部分

```
src/photoman/
  color.py       sRGB ↔ 線性光（負值不產生 NaN）
  mask.py        填內洞、去斑、膨脹、兩個遮罩的衍生
  composite.py   ★ 合成器（float 與 uint8 兩層）+ 校驗環量度 + 裁切規劃
  image.py       保真匯入匯出（HEIC、ICC、EXIF 方向）；load_srgb 取底圖位元組
  project.py     圖層資料模型、永久 ID、快取鍵鏈
  store.py       專案目錄讀寫、原子儲存、原檔核對
  inpaint.py     ★ inpainting 引擎（Telea / LaMa），引擎藏在 Protocol 之後
```

## 4. 不可違背的設計約束

改動任何一項都會推翻整個架構。

### 鐵律：寫入範圍之外逐 bit 不變

**這是本專案成立的唯一理由。** 它必須是 `composite.py` 的性質，
不是關於任何模型的聲明。

多層版本（2026-09-19）：**所有圖層的寫入範圍聯集之外，位元組等於原檔。**
每一步都在 alpha 為 0 的地方做位元組複製，歸納下來就成立。
寫入範圍是 `dilate(fill_holes(遮罩), feather_px)`，**不是使用者畫的那條線**。

模型廠商自己承認會漂移——FLUX.1-Fill-dev 的官方模型卡寫明填充區以外
有輕微色偏；diffusers 的維護者說明 inpaint 權重是**刻意**訓練成
跨接縫融合的。詳見 `design.md` §5.6。

**任何改動 `composite.py` 或 `mask.py` 的提交都必須有對應測試。**

### 三個品質層的契約是相反的

| 層 | 契約 |
|---|---|
| 確定性調整 | 無損，原解析度進出 |
| 局部生成 | `M_blend` 羽化帶以外逐 bit 不變 |
| 全幅生成 | 無（沒有可保留的東西） |

### 使用者不會用專業修圖工具

不給專業術語（圖層、色版、曲線、羽化值），每次生成前要有前後對照。

⚠️ **這一條原本寫的是「選取必須是點擊，不是套索」——2026-09-19 修正。**
點擊分割很好用，但它回答的是「這一團像素是甚麼」，不是「我要改哪裡」。
手動的筆刷與方框現在是預設，而且**手畫的範圍就是遮罩本身**。
這是「使用者圈選＝空間通道」的直譯，不是違背它。

### 不做批次

修圖逐張進行。所以**不需要**任務佇列、斷點續跑、隔夜模式。
反過來，**延遲非常關鍵**——非同步回報進度與可取消比吞吐量重要。

## 5. 最貴的幾課（不要重踩）

### 兩個遮罩，不是一個

柔軟度**不可以**交給模型。PELC（CVPR 2026）證明在潛空間用軟遮罩做
線性混合不等於像素空間混合——VAE 解碼器非線性且空間糾纏，
要還原真值編碼，一半以上的體素需要落在 `[0,1]` 之外的 α，
結果是**無效的潛向量**，造成接縫、光暈、以及遠離遮罩處的劣化。

→ 模型拿到二值遮罩；柔軟度全部在像素空間的合成 alpha。

### 主要失效模式是頻寬，不是接縫

縮小去送沒有害，**放大回來是有損的**，把有效頻率上限砍半。
用**縮小倍率**判斷：`≤1.5×` 沒問題；`~2×` 邊緣；`>2–3×` 明顯低頻；
`>4×` 一眼看出。**羽化救不了它。**

→ 對策是放大後補跑一次低強度 hires pass（`design.md` §5.3.2 第 7b 步）。

### 填內洞不是可選項

**SAM 產生的遮罩是有洞的、不連續的。** 不填的話，模型會在物件內部
看到「保留」的指令，結果是物件沒有被完全移除。

### 幾何是最後的輸出設定，不是圖層

裁剪、旋轉、拉直不佔圖層。→ **遮罩永遠存在原圖座標，不需要任何變換。**
這消除了整個「幾何變更令下游遮罩失效」的問題類別。

### 真實照片與設計假設的落差（2026-09-18 實測）

設計一直假設 4K（8.3 MP）。**實測最大的一張是 42.2 MP**，
float32 線性光是 **506 MB**。→ **已定案（`design.md` §6.1c）：
底圖存原檔的 uint8 位元組（127 MB），只在處理裁切區時才線性化。**

**這個決定有一個比省記憶體更重要的好處：** 遮罩外的保證由
「避免寫入」升級成**字面上的位元組複製**——那些像素根本沒有經過
任何浮點運算，所以不可能有往返誤差。已用那張 42 MP 的照片實測：
**遮罩外 42.1 MP 之中，被動過的位元組 0 個。**

**推論（會影響圖層的評估方式）：** 逐點運算（曝光、白平衡、曲線）
與裁切可交換，所以 N 個調整層可以**合成成單一函數**，
一次套用——**沒有中間量化損失**。這正是「累積質素下降」的主要來源，
在這裡被結構性地消除了。

另外兩項：**HEIC 必須支援**（iPhone 預設格式，Pillow 讀不到，
沒有 `pillow-heif` 的話使用者第一張照片就失敗）；
**ICC 不可以假設是 sRGB**（iPhone 是 Display P3，直接當 sRGB 用會偏色）。

### 保證鏈的關鍵：uint8 → 線性光 → uint8 必須精確

這個失敗是**靜默的**——若不精確，整張圖每個像素都差一兩級，
看起來「差不多」，而保證已經破了。已實測 256 個灰階值全中、
1474 萬像素的真實圖片最大差 0，並寫成正式測試。

### ★ 接縫可以不看出來——核心問題已答（2026-09-18）

在真實照片上移除三顆骰子（遮罩 0.30 MP，裁切 1228×1134）：

| 引擎 | 時間 | 校驗環 | 填補品質 |
|---|---|---|---|
| **LaMa** | 13.5 秒 | 24.0 | **幾乎看不出接縫** |
| Telea | 1.2 秒 | 0.0 | **一眼看出**（平滑多邊形灰塊） |

**LaMa 是本地主力引擎，不是 Telea。** 慢十倍，但對逐張修圖可以接受。

### ★★ 校驗環不是品質閘門（實測推翻了設計）

**LaMa 是遮罩原生的模型，卻把「被告知不要改」的區域改了 24–27 級**
——它整張重繪，加上 512 往返的重新取樣。

**這正是「保證只能來自合成器」的實證**（見 `design.md` §5.6）。
但它同時推翻了原本的設計：**校驗環的大小與填補品質無關**
（LaMa 24–27 而好、Telea 0 而差）。

→ 所以校驗環是**診斷數字**，`is_trustworthy()` 現在要明確給門檻才判斷。
門檻只在「模型聲稱會保留遮罩外」時才有意義。

### 遮罩必須完整蓋住物件

第一次測試時橢圓在骰子底部留了一條邊，LaMa 把那些殘留的暗色
**延伸進洞裡**，產生大片暗影。遮罩沒蓋好的代價比想像中大——
不只留下殘影，還會污染填補。

### ⚠️ LaMa 的 ONNX 空間維度固定是 512×512

裁切圖大於 512 就要縮小進去、放大回來。對 LaMa 的代價比帳面上小
（填補區本來就平滑），但真正大的裁切圖應該切塊處理再融合。
**這是目前最大的已知技術債。**

### ★★ 引擎回答的是「它怎麼畫」，不是「使用者要甚麼」（2026-09-20）

`match_colour` 該把生成塊的顏色對到哪裡，第一版用**引擎**判斷：
本機是填補、雲端是編輯。聽起來很合理——本機只會由邊界往內填，
雲端是照指令生成。

**用真實圖層量出來是反的。** 那個使用者三次雲端編輯裡有兩次是
`移除人物`——那是填補語意，而引擎是雲端。第一版的判斷會把那兩次的
落差由 2.4／3.9 級推到 22.8／38.6 級，也就是留下一塊看得出來的方框。

**教訓：不要用間接的訊號去猜使用者的意圖。** 引擎、模型名稱、
有沒有一個 prompt——這些都與「使用者要的是移除還是替換」無關。
猜錯的代價是靜默的（成品看起來很自然，只是不是你要的顏色）。

→ 直接問。一組兩個按鈕的成本，遠低於猜錯。

### ★ 假設「只做一次」的地方，全都是 bug（2026-09-19）

整個 P0/P1 都是繞著「一次編輯」寫的：`Session` 只有一個遮罩、一個結果，
每一次執行都從最原始那張圖重算。功能上每個零件都對，**合起來卻只能改一次**。

這類 bug 有兩個特徵，都很難在程式碼裡看出來：

- **每個零件單獨看都正確。** 遮罩沒有清掉不是錯的（使用者可能想繼續加選），
  從原圖重算也不是錯的（那是保證的來源）。
- **只有連續使用才會出現。** 所有的單元測試都只做一次編輯，所以全過。

→ **寫測試時要想「第二次會怎樣」。** 修好之後的測試就是這樣寫的：
`tests/test_multi_edit.py` 的第一條就是連續改兩處。

### 宣告了卻沒有讀的參數，會令測試說謊（2026-09-19）

`ApplyRequest` 一直有一個 `method` 欄位，但伺服器**從來沒有讀它**——
本機路徑寫死 `method = "lama"`。

代價不是功能，是**測試的時間與可信度**：`test_web_api.py` 的端到端
測試明明寫著「用 Telea 而不是 LaMa，因為這個測試要快」，實際上每個
測試都在載入 LaMa（**實測每個測試 12 秒**，整個測試檔 91 秒）。而且
那個註解會令下一個人相信測試跑過了它其實沒有跑的路徑。

→ 修好之後整個測試檔 91 秒 → 40 秒。

**教訓：測試裡「我以為我在測甚麼」比測試本身更容易出錯。**
看到宣告了卻沒有被使用的參數，要當成 bug。

### 模型廠商聲稱的「保留」不算證據

Bria GenFill 聲稱「遮罩外像素完全保留，逐像素完美」，
但**沒有說明任何機制，也找不到任何第三方做過像素比對測試**。

→ 凡是模型自己講的，都不算證據。要驗，不要信。

### 兩個授權陷阱，都是「同類最好但不能用」

**EdgeSAM**（CPU 最快的分割）與 **CodeFormer**（最好的人臉修復）
**兩者都是 NTU S-Lab 非商用授權**。很容易順手選到它們。

另注意 **SAM 2 是 Apache-2.0，但 SAM 3 不是**——不要假設同家族共用授權。
